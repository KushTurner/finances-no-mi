# Web coding standards

These rules apply to everything under `apps/web`, in addition to the root `AGENTS.md`.

## Structure

```
src/
  api/           One module per API resource, plus client.ts for the shared fetch helper
  hooks/         Query, mutation, and other reusable hooks
  providers/     Context providers for state shared across components
  lib/           Pure functions: formatting, dates, money, calculations
  components/
    ui/          shadcn components, generated by the shadcn CLI
    common/      App components shared by more than one route
    <feature>/   Components used by one route or feature
  routes/        Route definitions, search-param validation, and page components
```

- Each folder outside `components/ui` exposes its public API through an `index.ts` barrel.
- Import another folder through its barrel, never from a file inside it. Files within the same folder import each other directly.
- Import `components/ui` components from their own files, as the shadcn CLI generates them. Do not add a barrel there.
- Import `cn` from `@/lib/utils`, the path the shadcn CLI generates. Everything else in `lib/` comes from `@/lib`.

## Files and naming

- One component per file. The file is named after the component in PascalCase, for example `AccountCard.tsx`.
- Non-component modules use camelCase file names, for example `periods.ts`.
- Use named exports only.
- Keep a component file under about 150 lines. A larger component is a sign it should be split, or that it holds logic that belongs in `lib/` or a hook.
- Declare props as a named type, `type AccountCardProps = { ... }`, above the component.
- Colocate tests with the file they test: `periods.ts` and `periods.test.ts`.

## API

- `api/` holds request and response types and the functions that call the backend. Nothing else calls `fetch`.
- Request and response types mirror the API's JSON exactly, including snake_case field names such as `spent_pence`. Do not map them to camelCase.
- API functions return typed data or throw an `Error` with a readable message. They do not touch React or the query cache.

## Server state and caching

- Server data lives only in TanStack Query. Never copy query data into `useState`; derive from it during render.
- Client-only state, such as selections, form input, and toggles, never goes in the query cache.
- Components never call `api/` functions directly. They use a hook from `hooks/`.
- Name hooks after what they do:
  - `use<Resource>Query` for a `useQuery` hook, for example `useSummaryQuery`.
  - `use<Action>Mutation` for a `useMutation` hook, for example `useAssignCategoryMutation`.
  - `use<Thing>` for other hooks, for example `useHiddenAmounts`.
- Write each query key in exactly one place: the `use<Resource>Query` hook that runs the query.
- Start every key with its resource name, then add every value the query function uses, for example `['summary', 'months', range, accountIds]`.
- A mutation invalidates every resource whose data it changes, by resource name. Changing a transaction's category, for example, invalidates both `['transactions']` and `['summary']`.
- Keep the query client's defaults. Set `staleTime` or other cache options on a query only when there is a specific reason.

## Client state

- Keep state in the lowest component that needs it.
- State that belongs in the URL, such as the selected period, filters, and selected accounts, lives in route search params. Components read it with `getRouteApi('<route>').useSearch()` and update it with `useNavigate`, instead of receiving it through props.
- State shared by several components that does not belong in the URL lives in a context provider in `providers/`. The provider component has its own file; the context and the `use<Name>` hooks that read it live in a `.ts` file beside it, so fast refresh keeps working.
- Passing a prop through more than one component that does not use it is a sign the value belongs in search params or a provider.

## Components and logic

- Components render. Calculations, data shaping, parsing, and decisions about what to show live in pure functions in `lib/`, with unit tests.
- Format money only with the shared money helpers in `lib/`. Do not create `Intl.NumberFormat` instances in components.
- Show loading, error-with-retry, and empty states with the shared components in `components/common/`.
- Use `useMemo` and `useCallback` only when a value must keep the same identity: an effect dependency, a context value, or a prop of a memoized component. Do not use them for ordinary calculations or event handlers.
- Use `useEffect` only to synchronise with something outside React, such as the DOM, a browser API, or storage. Do not use it to derive state or respond to events.

## shadcn and styling

- Use a shadcn component before building a control by hand. Add new ones with `pnpm dlx shadcn@latest add <component>`.
- Do not edit files in `components/ui` by hand, except to apply the project's design tokens. Customise usage through `className` and variants.
- Style with Tailwind classes. Use `style` only for values computed at runtime, such as a bar width or a series colour.
- Use theme tokens from `src/index.css` for colours, sizes, radii, and shadows. Do not use hex colours or arbitrary values such as `text-[13px]` or `bg-[#3a3a3e]`; add a token instead.
- Combine conditional classes with `cn` from `@/lib/utils`, not template literals.

## Accessibility

- Use real interactive elements: a `<button>` for actions, a `Link` for navigation, and a `<label>` for every form control.
- Give icon-only buttons an `aria-label`, and hide decorative icons with `aria-hidden="true"`.
- Use `role="status"` for loading and success messages and `role="alert"` for errors.
- Every chart offers its values as a table.
